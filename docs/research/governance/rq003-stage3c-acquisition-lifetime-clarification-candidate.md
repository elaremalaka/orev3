## 2. Evidence and decision options

The preceding read-only investigation authenticated CPython 3.14.5 and reproduced
an open `/dev/null` descriptor with `owner.fd = None`: a real SIGALRM handler raised
KeyboardInterrupt after acquisition but before ownership assignment. Separate
C-return profile injections produced the same result with KeyboardInterrupt,
SystemExit and BaseException. The real signal reproduction means this is not
merely an artificial tracing execution point. It does not establish that every
exception class is spontaneously generated by normal OS signal delivery.

CPython's successful open wrapper returns an integer; the evaluator can handle
pending events before the following assignment. An integer is not a cleanup owner.
The relevant source evidence is [CPython 3.14.5 open implementation](https://raw.githubusercontent.com/python/cpython/v3.14.5/Modules/posixmodule.c)
and [call evaluation](https://raw.githubusercontent.com/python/cpython/v3.14.5/Python/bytecodes.c).
Python documents the risks of raising signal handlers in its
[signal exception guidance](https://docs.python.org/3.14/library/signal.html#note-on-signal-handlers-and-exceptions).
These observations motivated the following reviewed decision, adopted by this
status edit with Git effectiveness pending; it was not pre-existing authority.

| Option | Guarantee and cost | Assessment |
| --- | --- | --- |
| A. Pre-established native acquisition owner | Native acquisition records every successful result before interruptible Python resumes; requires explicit disposal, packaging/build/portability and host qualification | Stronger local guarantee, but not established as necessary by the trusted-controller model; a returned token plus finalizer is insufficient |
| B. Deferred supported cancellation and Python ownership | Prevents supported raising cancellation through acquisition/handoff; needs enforceable controller execution and signal contract | Necessary prevention, but not a disposition for an unexpectedly unprovable outcome |
| C. Python ownership plus mandatory retirement on uncertainty | Prevents continued operation with unknown process-local resources; exit reclaims local descriptors | Sound fallback for this resource scope, but alone needlessly accepts avoidable interruptions |
| D. B plus C | Defer supported cancellation; require terminal process retirement whenever acquisition ownership nevertheless cannot be proven | SELECTED: prevention plus a bounded failure disposition, preserving owned-state exception safety |
| E. Context manager, repeated wrapping or descriptor duplication alone | Registration still follows an acquisition; duplication introduces another resource | Does not close the identified boundary |

The selected model constrains authorized execution rather than claiming CPython
is uninterruptible. It does not promise availability after acquisition uncertainty.
No project-owned native acquisition wrapper is REQUIRED for the current measurement/
pre-production candidate under this model. Production or real-capital authorization
may impose stronger requirements. Future native hardening is permitted only through separate scope/authorization and review;
it is neither implemented nor prohibited here. Native treatment of process spawn
would additionally need child-lifetime authority, beyond storing a PID.

## 3. Resource and trust scope

The rule covers controller-owned ordinary FDs, duplicated FDs, pipe ends, socket
endpoints, and FDs that carry flock authority. Multi-result acquisitions must account
for every result. Flock acquisition on a known FD must have an owned descriptor
before locking; uncertain lock success must not be treated as confirmed exclusion.

This is not a universal kernel-resource transaction rule. Child creation, remote
services, persistent mappings or other resources with materially different lifetime
are not assigned process-exit recovery semantics by analogy. Directory/file creation
and link/rename effects remain subject to their existing filesystem authority.

The controller remains trusted. Authorized callbacks, handlers, helper functions and
concurrent controller paths MUST obey this contract; accidental violation is not
excused as trusted behavior. Deliberate malicious code with equivalent controller
privilege remains outside the existing internal threat model. No worker capability
is added, and no worker may manipulate controller ownership.

## 4. Supported interruption sources

| Source | Proposed treatment |
| --- | --- |
| Ordinary synchronous exceptions after ownership, including ValueError and application BaseException | Existing deterministic cleanup/quarantine and accounting finality apply |
| SIGINT normally translated to KeyboardInterrupt | Supported cancellation intent; MUST NOT raise into the protected acquisition/handoff interval |
| Any other installed Python signal handler capable of raising, including SIGALRM | Same deferral requirement; an unmodified raising handler during this interval is an unsupported controller configuration |
| Synchronous SystemExit or KeyboardInterrupt in authorized code | No deliberate delivery inside the protected interval; after ownership or definitive failure, existing exceptional-exit rules apply |
| Signal-handler SystemExit or another BaseException | Raising-handler cancellation, covered by deferral; exception class does not create an exemption |
| Tracing/profiling hooks injecting pre-ownership exceptions | Not a supported production cancellation source; useful fault testing of uncertainty retirement; not a demand for leak-free continued execution |
| CPython asynchronous exception injection APIs | Not an authorized production cancellation mechanism in this interval; unexpected acquisition uncertainty requires retirement |
| SIGKILL/process death | No Python cleanup guarantee; kernel-local reclamation and separate recovery semantics apply |
| SIGSTOP | May suspend execution; cannot be masked; suspension is not disposal or proof of orphanhood |
| Malicious trusted-controller bypass | Outside the internal threat model; no claimed resistance |

Unsupported injection MUST NOT be caught and converted into permission to continue
once uncertainty is detected. A detected contract breach fails closed. This does not
claim detection or recovery against arbitrary malicious machinery suppressing the
retirement path itself.

## 5. Protected interval and deterministic ownership point

Before issuing an acquisition syscall, the controller MUST establish the supported
cancellation policy and a reachable, enclosing failure authority that treats an
unclassified acquisition exit as terminal uncertainty. Failure to establish that
protection means no acquisition is attempted. This is an in-memory control obligation,
not a new persistent registry, journal or payload.

Protection starts before invoking the resource-acquiring helper. Entering a nested
acquisition/handoff establishes another active protection obligation. Completing an
inner interval MUST NOT deliver cancellation while any enclosing interval remains
active; every enclosing classification and handoff remains protected. Logical
protection depth reaches zero only after all enclosing obligations are classified.
This specifies nesting semantics, not a counter or lock implementation.

Each interval continues until:

- failure is proven definitive with no acquired result left unowned; or
- every successful resource identifier is recorded in an explicitly reachable cleanup
  authority that survives interruption of subsequent assignment or helper return.

The owner MUST have one explicit disposal responsibility, with sufficient identity
and state for governed use or non-retryable uncertainty classification. Mere presence
of a result on the evaluator stack, a helper local that is about to disappear, or a
future intention to append it is not that ownership point. No GC/finalizer is proof.
Resource ownership alone is not mode, UID, confinement, lease, or admission authority;
those existing authentication steps remain necessary before governed use.

Helper acquisition MUST either register into an already-reachable enclosing owner
before returning, or keep cancellation protection and the enclosing uncertainty
boundary uninterrupted through caller registration. A successfully returned raw
integer does not end protection if permanent ownership has not been established.
For multi-result operations, partial registration does not classify the remaining
results as absent. Any unproven result requires retirement.

Handoff into a longer-lived ledger MUST leave one reachable disposal authority at
every interruption boundary. Referencing the same owner is not a second disposal
owner. An explicit transfer must have a complete before/after responsibility result;
there must be neither a gap nor two independent closers. Cancellation remains deferred
through a transfer that would otherwise leave responsibility ambiguous. If a helper
fails after registration, the enclosing owner remains responsible; caller receipt
is not required to discover it. Accounting continues to borrow, never dispose.

## 6. Cancellation delivery and implementation limits

During this interval, authorized cancellation paths MUST record/defer cancellation
without raising into acquisition or handoff. Delivery is eligible only after the
OUTERMOST interval has completed the classification required by §5, protection depth is zero, and RETIRING has not
superseded ordinary delivery. This is the exact meaning of a cancellation delivery point,
not an unspecified convenient bytecode boundary. Pending cancellation MUST then be
handled under existing safe-exit/accounting rules before normal work resumes.

Repeated requests MAY coalesce into bounded pending state; no unbounded queue or
exact count of repeated SIGINTs is required. At least one requested cancellation
MUST remain represented until governed delivery or terminal retirement/hard process
termination supersedes it. Recording, delivery and clearing must have deterministic
before/after semantics, including handler reentry; a stale clear MUST NOT erase a
new request. If a request arrives during delivery, it must either remain pending
for subsequent eligible delivery or be subsumed by the current delivery under an
explicit documented coalescing rule. An inner exit cannot clear outer pending state.
No normal work may resume with an undelivered, unsubsumed cancellation. RETIRING
supersedes this delivery obligation and cannot be delayed by cancellation processing.

A future implementation must demonstrate coverage of installed raising handlers,
helper calls, authorized concurrency and pending cancellation across interval entry
and exit. No arbitrary application callback may run inside this interval unless it
obeys the same contract. Unexpected synchronous failures before classification also
use §7; deferring signals does not make all failures impossible. Deferral does not
retroactively defer a synchronous exception already raised. Authorized code must
not deliberately inject raising cancellation through protection. Ordinary synchronous
failure is classified: definitive no-acquisition failure uses ordinary handling;
known ownership uses known-owner cleanup/quarantine; only genuinely unprovable
acquisition requires retirement. Exception class alone does not select retirement.

No particular masking API is mandated. pthread_sigmask alone is not proof: its mask
is thread-local, other threads and interpreter-pending events matter, and it does not
mask tracing or asynchronous exception APIs. SIGKILL/SIGSTOP must not be represented
as maskable. A non-raising handler/deferred-delivery design is an eligible approach,
not already-verified implementation. Installing/restoring protection itself must not
open an unprotected acquisition interval. If support cannot be established, that
acquisition path remains blocked; no weaker fallback is authorized.

Deferral covers cooperative controller-level cancellation only. It MUST NOT defer
or weaken SIGKILL, unavoidable process death, independently authorized hard termination,
or future watchdog hard-kill authority where separately governed. Protection grants
no authority to postpone hard termination indefinitely.

Protection is confined to bounded acquisition/handoff work needed to establish
definitive failure, deterministic ownership or retirement uncertainty. It MUST NOT
continue through unrelated work, arbitrary waits, indefinite blocking housekeeping
or later scientific processing. An integration unable to establish the necessary
bounded/liveness behavior under existing authority remains blocked pending its own
qualification. This does not assert that all kernel calls finish within a universal
time bound. Later watchdog/cancellation machinery must compose with these rules;
no watchdog value, timeout or new hard-kill authority is introduced.

## 7. Unprovable acquisition and terminal retirement

If an interrupted acquisition/handoff cannot prove definitive failure or deterministic
ownership of all successful results, the controller MUST enter terminal retirement.
Owner-local quarantine while unrelated normal operation continues is insufficient:
unknown process-local resources have no safe targeted disposal proof.

The controller MUST NOT guess FD integers, scan and close arbitrary descriptors,
retry uncertain raw closes, use uncertain resources, report cleanup success, or admit
work as though acquisition failed cleanly. An enclosing guard must default to retirement
on unclassified exit; this MUST NOT depend on receiving the missing result. It may
conservatively retire even if the syscall in fact acquired nothing.

Once unprovable acquisition is classified, process-wide RETIRING MUST become
irrevocably authoritative. No new admission, acquisition, launch, publication or
operation, no normal controller service, and no unsafe cleanup dependent on uncertain
ownership may occur afterward. All authorized controller paths must honor this state;
catching an exception MUST NOT clear it. Pending or repeated cooperative cancellation
no longer governs control flow and must not interrupt the terminal route. This does
not exclude independently authorized hard termination or claim immunity to malicious
trusted-controller bypass.

The required ordering is: acquisition uncertainty -> authoritative RETIRING ->
optional bounded safe housekeeping, if eligible -> non-returning terminal process
exit. Housekeeping is OPTIONAL and never required for safety. It may use only
independently known-safe authority, must not acquire resources or conduct destructive
recovery without existing authority, and cannot restore service. Potentially blocking
logging, flushing, cleanup, joins, finalizers and atexit execution MUST NOT precede
the only exit route. If bounded completion cannot be established, omit that work.
A failure in eligible housekeeping must immediately continue to terminal exit,
without retry or ordinary exception propagation as the means of exiting.

The controller MUST reach a supported non-returning process-exit primitive that
bypasses ordinary Python shutdown; raising SystemExit or calling sys.exit is not
sufficient. On the current CPython/POSIX platform, os._exit(...) is the applicable
route: it bypasses Python cleanup handlers and stdio flushing intentionally for
this exceptional retirement path. An equivalent supported primitive is acceptable
only with the same non-returning process-termination property. See
[Python process-exit semantics](https://docs.python.org/3.14/library/os.html#os._exit).
The primitive and a valid status must be available before acquisition is enabled;
exit must not require late imports, callbacks or new resource acquisition. This is
an adopted semantic obligation pending Git effectiveness, not authorization to implement or invoke it here.

The exit route MUST remain reachable despite logging/cleanup exceptions, failed
flushing, unreliable ordinary shutdown hooks, repeated cooperative cancellation,
or application code that would catch SystemExit. It must bypass those dependencies,
not place a fallback after potentially unbounded work. A future implementation must
prove RETIRING publication, all-path service exclusion and terminal-route reachability
under the supported interruption model before enabling the acquisition integration.
Kernel/host termination semantics remain subject to qualification; no impossible
guarantee against a stalled kernel or arbitrary hostile controller code is asserted.

Use an existing governed failure/status authority if applicable. No exact controller
retirement exit status is established by the authorities bound here; selecting and
independently authenticating an appropriate status is an implementation/adoption
dependency before enabling this route, not permission to invent a new code here.
No new retry count, time bound, process or persistent retirement artifact is added.

Retirement is a controlled terminal decision, not an assertion that a crash occurred.
Actual process exit reclaims its local descriptors; references held elsewhere and
children may survive. Bypassing Python shutdown does not reverse filesystem effects,
prove child termination, or grant orphanhood or destructive recovery authority.
A fresh separately admitted controller must perform existing startup reconciliation.

Known-owner uncertain close remains the existing non-retryable quarantine case; this
clarification does not require process-wide retirement for every close error. If uncertainty
also destroys the proof of acquisition ownership, the stronger retirement rule applies.
An affected quarantined owner cannot resume admission; no closed integer may be retried
merely because a close exception might mean the descriptor remains open.

## 8. Persistent effects and child-process boundary

| Effect | Treatment after interruption/retirement |
| --- | --- |
| Open existing object | Usually no new filesystem object; exit reclaims only local descriptor references |
| Exclusive file/directory creation | Object may remain; existing grammar, lease and recovery authentication govern it; no rollback claim |
| Lease open or flock | Exit releases local references; another inherited/shared reference may retain exclusion; fresh controller must use governed lease proof |
| Duplication | New local FD is in scope, including references to locked descriptions; exit does not eliminate other holders |
| Pipe/socket creation | All local endpoints are in scope; peer endpoints and peer effects are not undone by exit |
| Publication link/rename | Persistent namespace effect, not an FD acquisition to be rolled back; existing publication/terminal protocol and durability requirements remain controlling |
| Spawn succeeded but PID receipt uncertain | Child may survive with descriptors/capabilities/lease; parent exit is NOT child cleanup |

Process creation is explicitly OUTSIDE this clarification's process-local reclamation
rule. Existing Stage-3A launcher, start-gate, capability, lease inheritance and process
identity requirements remain controlling. The clarification neither proves these close
an uncertain spawn-result gap nor authorizes a new spawn path. If integration cannot
prove child ownership/lifetime under that authority, process-creation integration
remains blocked for separate investigation; it must not invoke this clarification as
a solution. Do not guess a PID or kill unrelated processes. Parent failure grants no
permission to delete a root whose child lease remains live. No subprocess-acquisition
workaround is introduced by this document.

Ordinary pre-lease residue remains unclassifiable/fail closed. Valid ordinary or
terminal residue follows the adopted recovery predicates; published objects remain
outside private deletion authority. Exiting does not release accounting by fictional
filesystem deletion. Fresh orphan recovery remains aggregate-only under its existing
rules, not a live operation resume or reconstruction of an acquisition journal.

## 9. Existing exception safety remains intact

After ownership is established, existing BaseException requirements continue in full:
known-owner disposal, guard restoration/quarantine, borrowed-FD exclusion, uncertain
close non-retry, and complete before/after accounting state. Cancellation deferral is
not permission to leave an owned transition partially committed. There is no category
transfer, new accounting category, or changed reservation floor.

Before an authoritative accounting commit, failure cannot publish accepted capacity
or advance sequence. After a proven commit, later acquisition/teardown failure cannot
roll it back. In particular, authoritative orderly reconciliation from acknowledged
10 to observed 3 remains 3 after later scratch teardown failure; this illustration
adds no numeric policy. Unproven pre-commit reconciliation releases nothing. Retirement
blocks later use without inventing accounting rollback or successful disk cleanup.
